# 全产业链知识图谱自动抽取与分析系统

这是一个本地化的 Web 系统：用一个 `graph_data.json` 作为“产业链知识图谱主库”，在浏览器里做图谱可视化、增删改（节点层面）、导入/合并，并提供四大功能模块：

- 基础图谱通过其骨架进行补充：以现有“产业链骨架”（环节 `level=1/2/3` + “从属于”）为稳定结构，在**骨架保持不变**前提下，持续导入业务数据并自动抽取/去重/挂接实体与关系，逐步完善行业知识图谱
- 风险分析：选择一个 Level 2 环节节点 → 输出可视化图 + LLM Markdown 风险报告（可导出 PDF）
- 政策推演：从政策 Excel 中检索/选择一条政策 → 输出可视化图 + LLM Markdown 推演报告（可导出 PDF）
- RAG 问答：基于向量库（Chroma）+ 知识图谱上下文回答问题（支持导出 PDF）

系统默认不依赖传统数据库：大多数数据都以本地文件（`JSON/XLSX/PNG/MD`）形式落盘。

## 产业报告 Hybrid RAG（v2）

默认仍使用 `legacy`。可通过 `REPORT_RETRIEVAL_MODE=compare` 影子比较，或在 v2 READY 已验证后使用 `hybrid_v2`；回滚只需恢复 `legacy`。模型下载必须显式执行 `scripts/provision_retrieval_models.py`，索引先运行 `scripts/build_report_hybrid_index.py --source legacy-chroma --dry-run`。旧 Chroma 无法恢复 v1 未提取的 HTML 表格文本。详细评测与人工审核要求见 `evaluation/report_retrieval/README.md`。

## 产业报告文章溯源

产业报告正文中的外部资料使用报告级 `[C1]`、`[C2]` 编号。编号只会绑定当前报告实际检索到的资料，同一资料跨章节复用同一个编号，局部重写新增资料时从当前最大编号继续递增。

- 报告工作区和历史记录保存 `references`，包括资料类型、标题、发布日期、检索时间、原文地址和命中的正文片段。
- 正文保存每节实际使用的 `citation_ids`；检索到但未写入正文的材料会显示为“其他检索候选”，不会伪装成已引用资料。
- 网页正文中的 `[C数字]` 可定位到文末参考资料；Markdown 和 Word 导出会保留正文编号及实际使用的参考资料。
- 知识图谱材料只用于节点定位，不等同于原始文章来源。
- 引用编号校验只保证材料可追溯，不替代对引用是否充分支持具体结论的人工判断。

## 2. 功能详解（前端能力）

### 2.1 基础图谱：骨架补全与图谱管理（骨架保持不变）

#### 2.1.1 知识图谱可视化与管理（Graph）

- **加载数据源**：浏览器直接拉取 `static/data/graph_data.json` 并在内存中构建索引
- **性能优化**：默认只渲染子集（约 `600` 个节点，`2000` 条关系以内），避免大图卡死
- **交互探索**：
  - 单击节点：聚焦并放大
  - 双击节点：从全量数据里“展开邻居”（一次最多展开约 `30` 个邻居）
- **全局搜索（内存检索）**：输入即筛选 + 下拉建议（前端本地过滤，减少后端请求）
- **仅看骨架**：一键过滤到“环节”节点及其之间的关系（不依赖额外骨架文件，完全由 `graph_data.json` 动态筛选）
- **节点属性查看/编辑**：侧边栏可查看节点 `properties`，并保存回 `graph_data.json`
- **节点删除**：删除节点并同步删除所有关联关系
- **导出 JSON**：下载当前 `graph_data.json`
- **备份**：一键备份当前 `graph_data.json` 到 `backups/`
- **导入 JSON**：
  - 合并模式：上传一个或多个 JSON，合并进当前图谱
  - 覆盖模式：上传一个 JSON，直接覆盖当前图谱

#### 2.1.2 图谱导入（Excel → 候选预览 → 入图）

图谱导入按“两步流程”实现：

1) **解析预览**：上传 Excel，后端调用 LLM 抽取实体/关系，返回候选列表  
2) **确认入图**：前端勾选候选节点/关系，提交后端合并写入 `static/data/graph_data.json`

说明：
- **骨架保持不变**：导入流程基于当前图谱骨架进行补充。骨架指图谱中的“环节（level=1/2/3）+ 从属于”结构；导入会优先把新实体/关系挂接到既有环节上，默认不会新增/修改骨架结构。
- 候选列表里**可能包含环节节点**（用于展示关系两端、保证关系可挂接）；它们通常来自主图谱，并不一定代表“新建”。
- 每次上传会创建一个 session，保存到 `uploads/sessions/<session_id>/`，里面会有上传文件、副本与日志。

### 2.2 风险分析（Risk）

- **下拉选择 Level 2 环节节点**（来自当前图谱）
- **运行推断**：生成
  - 可视化图片（前端展示）
  - LLM 风险报告（Markdown 渲染）
- **导出 PDF**：一键导出为 PDF

### 2.3 政策推演（Policy）

- **检索式下拉选择政策**：前端会先拉取完整政策列表到内存，再在浏览器端做过滤（减少频繁请求，提升交互响应）
- **运行推演**：生成
  - 可视化图片（前端直接展示）
  - LLM 生成的 Markdown 报告（前端渲染为 HTML）
 - **导出 PDF**：一键把“报告 + 图片”打包导出为 PDF（`html2pdf.js`）

### 2.4 RAG 智能问答（RAG）

- 基于 `RAG/vector_db`（Chroma 持久化库）进行相似段落检索
- 同时会从 `static/data/graph_data.json` 里抽取与问题相关的子图上下文
- 以 Markdown 输出回答，并支持“导出当前回复为 PDF”

RAG 相关脚本在 `RAG/`：

- 原始语料目录：`RAG/raw_docx_files/`（仅 `doc/docx`）

## 5. API 参考（主要接口）

### 5.1 健康检查

- `GET /api/health`

### 5.2 RAG 问答

- `POST /api/rag_query`
- Body：`{"query": "..."}`  
- 返回：`{"status":"success","markdown":"..."}`

### 5.3 图谱导入（Excel 两步）

- `POST /api/graph_import/upload`
  - `multipart/form-data`：字段 `file`（xlsx）
  - 返回：`session_id` + 候选 `data: {nodes:[], links:[]}`
- `POST /api/graph_import/commit`
  - Body：`{"session_id":"...","nodes":[...temp_id],"links":[...temp_id]}`
  - 返回：`added_nodes` / `added_links`

### 5.4 图谱维护

- `POST /api/graph_node_update`：更新节点属性  
  - Body：`{"id": <node_id>, "properties": {...}}`
- `POST /api/graph_node_delete`：删除节点及其关联关系  
  - Body：`{"id": <node_id>}`
- `GET /api/graph_export`：下载当前 `graph_data.json`
- `POST /api/graph_backup`：备份当前图谱到 `backups/`

### 5.5 图谱 JSON 导入

- `POST /api/graph_import_json`：合并上传的 JSON（支持多文件 `files` 或单文件 `file`）
- `POST /api/graph_import_json_replace`：覆盖当前图谱（取第一个文件）

合并策略（当前实现）：
- 节点去重键：`labels[0] + properties.name`
- 新节点/关系会生成形如 `n1/r1` 的字符串 ID（覆盖模式则完全使用上传内容）

### 5.6 风险推断

- `GET /api/risk/nodes`：获取可选的 Level 2 节点列表
- `POST /api/risk/run`
  - Body：`{"node_name":"..."}`
  - 返回：`report`（Markdown 文本）、`images`（`/static/...` URL 列表）、`log`

### 5.7 政策推演

- `GET /api/policy/list?keyword=...`：获取政策标题列表（可关键词过滤）
- `POST /api/policy/run`
  - Body：`{"policy_index": <int>}`
  - 返回：`title`、`report`、`images`、`log`

## 6. 常见问题（FAQ / Troubleshooting）

### 6.1 图谱导入报错：`KeyError: '"name"'`

这是典型的 `str.format()` 与 Prompt 里 JSON 示例花括号冲突导致的（`{"name": ...}` 会被当成格式化占位符）。项目里已用更安全的替换方式规避；若你自行改 Prompt，请注意保留 `{text}` 等占位符，其它 `{...}` 需要转义或改用安全替换。

### 6.2 Excel 导入没有效果

请确认：
- Excel 里存在 `正文` 列
- `正文` 单元格不是空，并且长度大于 5

### 6.3 为什么大图会卡？

前端默认只渲染子集，属于正常策略。建议：
- 用“仅看骨架”快速确认骨架关系
- 用“双击展开邻居”逐步探索细节
- 如确需一次渲染更多节点，可调整 `static/js/modules/graph_viz.js` 里的 `RENDER_LIMIT / MAX_VISIBLE_LINKS`

### 6.4 Matplotlib 线程警告/偶现图片未生成

风险/政策分析会在后端线程中生成图片，已使用无界面后端（Agg）以提升稳定性；若仍有问题，优先检查：
- 输出目录是否可写：`static/policy_outputs/`、`static/risk_outputs/`
- 是否有异常被吞掉（查看 `logs/app.log` 和控制台）

## 8. AI分析

### 8.1 政策推演业务逻辑详解
一、整体架构设计
政策推演系统采用三层分析架构：

政策解析层（LLM初步筛选）
深度推演层（图谱数据挖掘）
可视化展示层（多维度统计分析）
这种设计实现了从"政策文本"到"产业链影响"的完整转化链条。

二、核心业务流程
1. 数据输入阶段
政策数据: 从Excel文件读取政策标题和内容
产业链数据: 从知识图谱JSON文件加载完整的产业链结构
环节列表: 提取所有L2环节作为候选分析对象
2. LLM初步分析阶段
关键函数: analyze_policy_with_llm()

业务逻辑:

将政策内容和所有产业链环节提供给LLM
要求LLM识别受影响的环节并评分
输出结构化的JSON结果
3. 深度推演阶段
关键函数: trace_impact_chain()

业务逻辑:

对LLM识别出的受影响环节进行深度分析
向上追溯：确定环节在产业链中的位置（上游/中游/下游）
向下挖掘：统计关联的L3细分环节、产品数量、企业数量
构建完整的"政策→环节→技术→产品→企业"影响链条
4. 统计分析与可视化阶段
关键函数: visualize_deep_impact()

业务逻辑:

按产业链层级分组统计影响指标
生成多维度可视化图表
创建包含详细计算结果的文字报告

1. 提示词结构分析

def construct_prompt(title, content, all_stages):
    stages_str = "、".join(all_stages)
    prompt = f"""
    你需要扮演一位资深的产业政策分析师。

    【任务】
    分析给定的“人工智能政策”内容，判断该政策会影响“产业链环节列表”中的哪些具体环节。

    【输入数据】
    1. 政策标题：{title}
    2. 政策内容片段：
    {content[:4000]}... 

    3. 候选产业链环节列表（Level 2）：
    [{stages_str}]

    【输出要求】
    请只输出一个 JSON 列表（无Markdown标记），包含：
    - "stage_name": 受影响环节名称。
    - "impact_score": 影响力评分 (1-5整数)。
    - "correlation": 相关性评分 (1-5整数)。
    - "reason": 简短理由。

    若无影响返回 []。
    """
    return prompt

决策支持: 为投资和研发决策提供数据支撑
这个政策推演系统的核心创新在于将政策文本分析与产业链图谱分析深度融合，既发挥了LLM的语义理解能力，又利用了知识图谱的结构化优势，为政策影响评估提供了科学、量化的分析工具。



###补充
这几个关系是连接不同类型的节点的，为了区分边的类型所以用了不同的名称，比如，涉及环节是政策节点和产业链环节的连边，表示政策涉及了哪个环节。参与环节是公司和产业链环节的连边，表示公司参与了产业链的哪个环节，对应环节是舆情和产业链环节的连边；产品对应环节是产品和产业链环节的连边。


一个公司可以参与到多个产业链环节中去，而公司参与到产业链具体环节的方式实际是通过产品，一个具体的产品是独属于一个具体的产业链环节
